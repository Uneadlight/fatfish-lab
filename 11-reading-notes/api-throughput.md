# API 测速：TTFT 与纯生成速率

**测于** 2026-10-31
**起因**：有人说「别人的 API 峰值能跑到 300+ tok/s，我们在 DSH 里只有 200+」，怀疑是 DSH 前端 Markdown 渲染拖慢了。
**结论**：**DSH 没有损耗，200+ 就是这条链路的真实生成速度。**

---

## 一、方法

脚本：`D:\work\tools\bench-api\ttft_bench.py`（纯标准库，不依赖 openai/requests）

```
python ttft_bench.py --list                       # 列模型（deepseek-flash / deepseek-v4-pro）
python ttft_bench.py --tokens 8000 --repeat 3
python ttft_bench.py --sweep --long --max-tokens 2000   # 1K/8K/32K/100K 四档 + 长输出
```

**两个口径必须分开算，这是整份报告的关键：**

| 指标 | 定义 | 用途 |
|---|---|---|
| **TTFT** | 发出请求 → 收到第一个内容 token | 网络 + 排队 + prefill，跟"等多久才看到字"有关 |
| **生成段 tok/s** | `completion_tokens / (最后一个 token 时间 − 第一个 token 时间)` | 排除 TTFT，才是**纯生成速度** |
| 含 TTFT tok/s | `completion_tokens / 总耗时` | 会被长上下文 prefill 摊薄，**容易骗人** |

实现要点：`stream: true` + `stream_options: {include_usage: true}`（让最后一个 chunk 带 usage）；按 `data:` 行解析 SSE；用 `time.perf_counter()` 打点。

## 二、数据（deepseek-flash，流式，max_tokens 2000，要求长输出）

| 上下文 | prompt tok | 输出 tok | TTFT | **生成段 tok/s** | 含TTFT tok/s |
|---|---|---|---|---|---|
| 1K 字符 | 647 | 1,866 | 9.48s | **287.7** | 116.8 |
| 8K 字符 | 4,751 | 1,451 | 6.05s | **224.2** | 115.3 |
| 32K 字符 | 18,819 | 1,192 | 4.52s | **184.7** | 108.6 |
| 100K 字符 | 58,682 | 1,298 | 7.76s | **208.0** | 92.7 |

平均 **226 tok/s**。

### 对照：短输出会虚高 5–10 倍

同样的脚本，只把输出压到 130–300 tok（prompt 里问"用一句话回答"）：

| 输出长度 | 生成段 tok/s |
|---|---|
| 130–300 tok | **1,109 – 2,817** |
| 1,200–1,900 tok | **185 – 288** |

原因：输出太短时，几十个 chunk 在 0.1–0.3 秒内挤着到，计时误差被放大；服务端也可能批量 flush（有一次测出 `148 tok / 0.01s = 24,662 tok/s`，明显是伪影）。

## 三、三个结论

### 1. DSH 链路无损

直连 `api.deepseek.com` 平均 226 tok/s，DSH 里 200+，**两者一致**。进程间通信、插件层、渲染层都没有扣掉速度。

从架构上也不该有损耗——Markdown 渲染跑在 Electron 客户端，**不参与网络传输**。它影响"屏幕上什么时候出现字"，不影响"服务端什么时候吐字"。

### 2. 短输出测速不可靠

「300+ tok/s」这类数字，如果测的是几百 token 的短回答，那测到的是**瞬时突发速度**，不是稳定吞吐。要比速度，必须对齐三件事：

- 输出长度（≥1000 tok）
- 上下文长度
- 是否流式、用哪个口径

对不齐就没法比。这跟"别人家的模型更强"是同一类问题——**那是别人的前提，不是我这儿的前提**。

### 3. 长上下文吃的是 TTFT，不是生成速度

从 647 tok 到 58,682 tok（90 倍），生成速度只从 287 掉到 208（−28%），而 TTFT 在 4.5–9.5s 之间波动。

也就是说：**上下文长了，你等得久，但吐字速度没怎么变。** 想优化体验，该优化的是首字延迟（缓存命中、缩短 system prompt），不是"想办法让模型吐快点"。

---

## 四、这组数据的边界

- 只测了 `deepseek-flash`，没测 `deepseek-v4-pro`（单价高 4 倍，等有需要再测）
- TTFT 波动大（4.5–9.5s），受服务器负载影响，单次数据不可靠，看趋势别抠单点
- 「226 tok/s」是 2026-10-31 下午的实测值，**不是物理上限**——链路、节点、模型版本都会变
- 中文 token 密度约 1 token ≈ 1.7 字（627 tok 对应 1,018 字符），不同内容的换算比会变

## 五、下次再遇到"别人比我们快"

先问三个问题，再决定要不要信：

1. **测的是什么口径？**（生成段 / 含TTFT / 端到端）
2. **输出多长？**（<500 tok 的数字一律打折看）
3. **上下文多长、什么模型、什么时间点？**

三个都对得上，再谈差距。
