# 任务分派箱（跨对话外派机制）

> 用途：在「聊天对话」里说一句话，把任务外派给**指定的另一个对话**；那个对话一开口就能接单。
> 建立时间：2026-10-27。

## 规则（所有对话开场必读）

1. **任何对话开场第一件事**：跑 `node D:\work\任务分派\dispatch.js peek`，看有没有写着自己名的待办。
2. **接单**：`node ...\dispatch.js take <id> --by "<对话名>"`，然后执行并在对话里回一句「收到外派：<标题>，现在开始」。
3. **结单**：执行完跑 `node ...\dispatch.js done <id> --result "<一句话结果 + 证据（提交号/文件/数字）>"`。
4. **不抢单**：`target` 不是本对话的，不动；可以提醒用户「这单是给 X 对话的」。

## 分工约定（用户 2026-10-27 定，21:5x 修订）

| 类型 | 方式 | 做法 |
|---|---|---|
| **大任务** | ① 分派箱 → **派给「新建对话」** | 我在聊天对话开单（`--target "新对话"`）→ **提醒用户「新开一个对话，说一句接单」** → 新对话里的我 peek 到就接 |
| **小任务** | ② headless 后台 | 我直接起独立后台会话跑，不占对话 |
| **本对话（聊天）** | 只聊天；偶尔小任务 | 执行类大活一律外派 |
| **「开始学编程的第一晚」** | 只做当天的 2 个闭关单元 | **不再承接其他大任务**（它的上下文太长、缓存命中只有 80%+，贵且容易混乱） |

### 为什么大任务派给「新建对话」

- 新会话上下文短 → 前缀基本全命中，**缓存命中通常 99%+**，每轮成本比长会话低一个量级
- 长会话（比如学习对话）每轮重发几十万 token，即使 80% 命中也很贵，还容易把上下文搞混（它可能以为自己就是聊天对话）

### target 的写法约定

- `--target "任务接单"`：**默认目标**——固定用一个「任务接单」对话当执行通道（用户 2026-10-27 定）
- `--target "新对话"`：任意新开的对话都可以接
- `--target "<具体对话名>"`：只有那个对话接
- 接单判断：`target` 含「新对话」→ 任何新会话都可接；否则要名字匹配

### 「任务接单」对话的轮换规则（避免把它拖成第二个昂贵长会话）

1. 同一个「任务接单」对话连续接单，缓存命中会随轮次上升（冷启动 92% 左右 → 稳定后 97–99%）
2. **但命中率高 ≠ 更便宜**：会话越长，每轮总输入越大，绝对花费仍会上涨
3. 所以：**当它上下文 >40%，或已完成 ≥5 单，我在聊天里提醒用户「该开新的接单对话了」**；新对话里说「接单」即可无缝继续
4. 换新会话时不需要搬上下文——任务单在分派箱里，`dispatch.js peek` 就能接上



## 开单命令

```
node dispatch.js add --title "标题" --target "开始学编程的第一晚" --spec "要求/验收标准" [--mode box|headless]
node dispatch.js list
node dispatch.js take <id> --by "对话名"
node dispatch.js stage <id> <阶段> [--reason "..."]
node dispatch.js done <id> --result "结果"
node dispatch.js reopen <id>
```

## 状态怎么存（2026-11-02 改）

以前状态只写在 `box.json` 里，两个进程同时改，后写的直接盖掉前一个——**没有锁，丢单是静默的**。现在改成：

- **`box.log.jsonl` 是真相**：每次变更追加一条事件并 `fsync`，写完才算数。
- **`box.json` 只是快照**：每次变更后从事件流重放生成，原子替换（`rename`）。
- **目录锁**：写入前 `mkdirSync('box.lock')` 拿锁，等锁超时 5 秒，陈旧锁（60 秒以上）自动清理。

崩了怎么办：`box.json` 可能是旧的，但事件流完整 → `node dispatch.js replay` 重建。
怀疑对不上：`node dispatch.js audit` 对账（快照 vs 事件流），顺带列出**在等人的单**和**正在做的单**。

实测：10 个进程同时 `add`，**10/10 无丢失**（旧版会丢）；`audit` 报 `[OK] 快照与事件流一致`。

## 阶段表（第一个匹配胜出）

**`person:` 开头 = 没有人类输入就动不了。**

| 阶段 | 含义 |
|---|---|
| `person:delivery` | 投递失败，需要重试 |
| `person:answer` | 有一个等用户回答的问题 |
| `person:review` | 做完了，等验收 |
| `person:blocked` | 卡住，或失败后无人处理 |
| `working:queued` | 排着队，还没开始 |
| `idle` | 取了但还没动 |
| `working` | 正在做 |
| `done` | 终态 |

`list` / `peek` 里带 `!` 前缀的就是在等人的单。
