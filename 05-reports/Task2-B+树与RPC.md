## 1. 核心问题：磁盘上为什么是 B+ 树，不是红黑树

### 1.1 前提摆清楚（不然结论会跑偏）

这条比较只在**下面三个前提同时成立**时有意义：

1. **存储介质按"页"读写**。磁盘/SSD 的最小 I/O 单位是 4KB 扇区/页（HDD 还有寻道 + 旋转延迟，
   随机 4KB 读 ~100 µs–10 ms；NVMe SSD ~20–80 µs）。读 1 个字节和读 4KB 的代价几乎一样。
2. **内存与磁盘的延迟差 4–6 个数量级**。一次内存访问 ~100 ns，一次 SSD 随机读 ~50 µs，
   差 ~500 倍。所以"少读几个页"比"少做几次比较"重要得多。
3. **数据量远大于内存**。如果整个索引能塞进 RAM，红黑树/B 树都行，甚至哈希表更快——
   这正是"红黑树在内存里是标准答案、在磁盘上不是"的分界线。

### 1.2 扇出决定树高，树高决定 I/O 次数

设节点能装 `f` 个键（扇出），`N` 条数据，则树高约 `h = ⌈log_f N⌉`。

* **红黑树/AVL**：二叉，`f = 2` → `h = ⌈log₂ 100000⌉ = 17` 层。
* **B+ 树**：一页装多少就扇出多少。本项目 4KB 页 + 16B 定长槽 → `f = 255`，
  `h = ⌈log₂₅₅ 100000⌉ = 3` 层（因为 255² = 65025 < 100000 ≤ 255³）。

**树高就是一次点查要读的页数。** 17 次 vs 3 次 —— 这就是全部差别的来源。

### 1.3 实测（不是估算，是可复现的实验）

实验：10 万条 key，4KB 页，`bench/bench_disk_io.py`；B+ 树每页 255 键，
对照组是"每个节点独占一页"的朴素 BST（1 键/页，模拟"二叉结构直接落盘"的最坏情况）。

| 指标 | B+ 树 | 朴素 BST（每节点一页） | 倍数 |
|---|---|---|---|
| 树高 | **3** | 38（随机插入；平衡二叉理论值 17） | 6–13× |
| 总页数 | 789 | 100,001 | 127× |
| 索引文件 | **3.08 MB** | **390.63 MB** | 127× |
| 写页次数 / 插入 | **1.02** | 3.00 | 2.9× |
| **冷缓冲池点查页读 / 次** | **3.00** | **20.02** | **6.7×** |
| 冷点查耗时 / 次 | 45.0 µs | 86.0 µs | 1.9× |
| 范围扫 1000 键的页读 | **11** | 23,526 | **2,139×** |

四件事同时发生，且都不是巧合：

1. **页读次数 = 树高**：B+ 树 3 页/次，BST 20 页/次。这是算法层唯一重要的数字。
2. **文件小 127 倍**：BST 每页只放 1 个 key 和两个指针，4KB 里 3.97KB 是空气；
   B+ 树一页塞 255 个键，页利用率接近 100%。
3. **写放大更小**：BST 每插一个节点要改父节点页 + 新节点页（2 写），红黑树还要加上旋转
   （可能再改祖父节点），实测 3.00 写/插入；B+ 树分裂一次只写 2 页，平均 1.02 写/插入。
   磁盘上"写"比"读"更贵（SSD 有 FTL 写放大，HDD 有一次寻道），写放大 2.9× 是实打实的寿命和延迟成本。
4. **范围扫描差 2 千倍**：B+ 树叶子有链表，定位起点后顺着链走（3 + 8 = 11 页读）；
   BST 没有跨节点链表，扫 1000 个连续 key 只能逐 key 从根重爬（1000 × ~20 = 23,526 页）。
   **"范围查询"和"有序遍历"是关系型数据库的日常操作，这一项直接把红黑树判出局。**

### 1.4 为什么"SSD 让随机 I/O 变便宜"没有推翻结论

SSD 只是把单次随机读从 ~10 ms 降到 ~50 µs，**页粒度没变、次数差距没变**：
6.7× 的页读差在 SSD 上仍然是 6.7× 的延迟差。而且 SSD 另有两条约束让"少读页"更重要：

* **FTL 写放大**：4KB 随机写会触发整个擦除块（常见 512KB–2MB）的垃圾回收，
  写 1 页实际可能搬几十页。B+ 树写/插入 1.02 vs BST 3.00，差距被 FTL 进一步放大。
* **缓存命中率**：缓冲池能装 64 页时，B+ 树只需要 789 页的 8% 就能覆盖热点；
  BST 要 100,001 页，同样 64 页只覆盖 0.06%，几乎必然 miss（实测 B+ 热池命中率 76.6%）。

这也是为什么真正的数据库（InnoDB / PostgreSQL / SQLite）的索引页就是 B+ 树页；
而红黑树的位置在**内存中的有序容器**（Java `TreeMap`、C++ `std::map`、Linux 内核的 CFS 调度器）——
那里没有"页读"这个概念，比较次数才是成本。

### 1.5 诚实说明：页缓存把差距藏了一半

实测"耗时"只差 1.9×，而页读次数差 6.7×。原因是 **OS 页缓存**：
2000 次点查打在同样 789 页上，绝大多数 `pread` 直接命中内核缓存（几微秒），
没真正碰设备。**页读次数是算法指标，耗时受缓存影响。** 要量真实设备 I/O 需要
`O_DIRECT`（Windows 的 Python 不支持）或用 `RAMMap` 清缓存，本项目没有做，
所以报告只拿"页读次数"下结论，耗时作为佐证而非主证据。

### 1.6 内存里呢？（同代码的 order=64 版本）

| 操作（10 万条） | 单次 | 吞吐 |
|---|---|---|
| 插入（乱序） | 2.16 µs | 463,800 ops/s |
| 查找（命中） | 0.91 µs | 1,099,143 ops/s |
| 查找（未命中） | 0.63 µs | 1,579,205 ops/s |
| 范围扫描 1000 条 | 329 µs | — |
| 删除（乱序） | 1.07 µs | 931,919 ops/s |

树高 3，内存峰值 5.9 MB（62 B/键，含 Python 对象头）。
查找比 `dict` 慢 4.53×（dict 0.20 µs）——这是"保序 + 支持范围扫描"必须付的代价；
需要 O(1) 且不保序时用哈希表，需要有序范围时用树，两者不是替代关系。

## 2. 页式 B+ 树的实现要点

### 2.1 页布局（4096 字节，定长槽位）

```
[0]      kind      1B   1=内部 2=叶子 0=meta
[1:3]    nkeys     2B
[3:5]    next      2B   叶子链下一页号（0xFFFF=无）
[8:12]   child0    4B   内部节点的第 0 个孩子
[16:]    slots     16B/槽
            叶子槽: key i64 | value i64
            内部槽: child i32 | sep key i64 | pad 4B
```

* **定长槽位**：第 `i` 个槽的偏移是 `16 + 16*i`，纯算术定位，不需要偏移表或扫描。
  代价是 pad 浪费 4 字节/槽，换来 O(1) 定位和更简单的解析。
* **容量**：`(4096-16)/16 = 255` 键/页 → 扇出 256。
* **分隔键语义**：内部节点的 `keys[i]` 是"右子树最小键"，下行用 `bisect_right` 选孩子，
  保证"命中分隔键"时走右边。

### 2.2 为什么先"写穿透"再"改缓存"

`BufferPool.put()` 是 write-through：先 `pwrite` 落盘，再更新内存缓存。
反过来的 write-back 性能更好，但会引入"缓存已改、盘上还是旧值"的窗口，
在没有 WAL 的简化实现里这个窗口就是数据丢失。这里选简单可靠。

### 2.3 meta 页 = 提交点（崩溃安全的边界）

写入顺序：**先写所有数据页，最后写 meta 页**（meta 里存 `root_pid` 和 `leaf_head`）。
如果崩溃发生在 meta 写入之前，重开文件读到的仍是旧根，旧树完整自洽——相当于"事务没提交"。

**但这不等于事务安全**，必须说清楚：
* 没有 WAL，崩溃前已写的数据页不会回滚；
* 没有页校验和，单页写到一半（torn page）会读到半新半旧的数据，无法检测；
* 没有 double-write buffer。真实数据库（InnoDB redo log + doublewrite、PostgreSQL WAL + full_page_writes）
  用这两样东西解决上面两条，本项目没做，也不假装做了。

### 2.4 范围扫描为什么便宜

叶子页用 `next` 串成单链表，`range_scan(lo, hi)` 只需要：
`1 次下行（树高 3 页）+ 顺着链表读叶子页（1000 条 ÷ 255 ≈ 4–8 页）`，实测 11 页。
对照组 BST 没有链表，只能逐 key 重爬，页读 23,526 次。

### 2.5 删除只做在内存版（诚实的能力边界）

指令要求的"删除 + 合并 + 借位"在**内存版**里完整实现并测过
（`test_delete_everything_forward_and_backward` 覆盖 order 4/5/64 × 正序/倒序，
`test_random_ops_against_dict_oracle` 用 5000 步随机操作对照 dict，每次都校验全树不变量）。

**落盘版只实现了插入/查找/范围扫描**，没有删除。理由：
* 本任务要证明的是"树高 = 页读次数"，删除不改变这个结论；
* 页级删除合并涉及"跨页借位 + 父页分隔键同步 + 空页回收"，在没有 WAL 的前提下
  会让崩溃边界更难说清楚，收益小于风险；
* 这一条写进报告而不是藏着——**能力边界要自己说，不要等别人问**。

## 3. 手写 RPC

### 3.1 帧格式

```
| 4B 大端 payload 长度 | 1B 消息类型 | payload |
   类型: 1=REQUEST 2=RESPONSE 3=HEARTBEAT
```

* 长度前缀解决了 TCP 的**粘包**（一次 recv 拿到多帧）和**半包**（一帧分多次到）；
* 读侧 `recv_exact(reader, n)` 循环读满 n 字节，EOF 中途退出抛 `FrameError` 而不是空转；
* 上限 `MAX_PAYLOAD = 64 MB`，超限立即断开，防止一个撒谎的长度前缀把内存撑爆。

### 3.2 序列化：手写 TLV，禁用 pickle/json

| TAG | 类型 | 编码 |
|---|---|---|
| 0x00/0x01/0x02 | null/False/True | 单字节 |
| 0x03 | int | zigzag 变换 + LEB128 变长 |
| 0x04 | float | IEEE754 双精度 8B |
| 0x05/0x06 | bytes/str | 变长长度前缀 + 内容（str 记 UTF-8 **字节数**，不是字符数） |
| 0x07/0x08 | list/dict | 长度前缀 + 递归编码 |

为什么不用 `json.dumps`：它把 int 变成字符串、把 bytes 编码成 base64、还不支持 tuple/None key，
而且**速度慢一个数量级**。为什么不用 `pickle`：反序列化等于执行任意代码，
一个 RPC 服务端接受 pickle 就等于对外开了一个后门。

防御点（都有用例）：截断、尾随垃圾、未知 TAG、长度前缀撒谎、非法 UTF-8、不可哈希的 dict 键、
递归深度 > 64、单元素 > 64MB、int 超过 4096 位。

### 3.3 并发模型

每个连接一个线程（`threading.Thread`），服务端主循环 `accept` 后在独立线程里
`read_frame → 分发 → pack_frame → sendall`。业务 handler 抛异常时**只在响应里返回
`ok=False` + 异常类型/消息**，连接继续可用——一个请求写崩不能让整个服务崩。

## 4. 踩坑记录（都是真踩的）

1. **Windows 的 CPython 没有 `os.pread` / `os.pwrite`**
   `AttributeError: module 'os' has no attribute 'pwrite'. Did you mean: 'write'?`
   它们是 POSIX-only（Python 3.3+）。解决：封装 `_pread_exact` / `_pwrite_all`，
   有就用，没有就 `lseek + read/write`，并且**处理短读短写**（`read` 不保证一次读满）。
2. **PowerShell 改 UTF-8 源码会毁文件**
   `Get-Content -Raw` 按 ANSI 解码 → `Set-Content` 写回，中文全变 `鍐呭瓨鐗?`，
   只能整文件重写。以后改源码只用编辑工具，批量文本处理交给 Python。
3. **测试自己写错，别怪实现**
   `range_scan(11, 19)` 我一开始断言返回 `[]`，实际实现返回 12/14/16/18 —— 是实现对、测试错。
   范围扫描是区间语义，不是"精确命中"。
4. **`pack_frame(0, ...)` 不能用来测读侧**
   非法消息类型在打包阶段就被拒绝，测"读到未知类型"必须手工构造字节。
5. **varint 上限**
   用 128 位上限时 `2**200` 编码失败（Python int 是任意精度），改成 4096 位上限。

## 6. 一句话结论

**B+ 树赢在"把树高变成 3 而不是 17"，并且用叶子链表把范围扫描从 N 次随机 I/O 变成一次顺序 I/O。**
红黑树不是错的，它只是为"内存里比较成本占主导"的场景设计的；
把它直接搬到磁盘上，等于每层比较都付一次 4KB 随机读。
本项目用 10 万 key 的实测把这句话变成了 3.00 vs 20.02 页读、11 vs 23,526 页扫的具体数字。
