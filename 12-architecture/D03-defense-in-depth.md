# D03 多层防御网

> 出处：R01 架构卡片（登录留言板 `POST /messages`）

## 解决什么问题

一个**写接口**同时面临多种攻击面：超大 body 打满内存、未登录用户写数据、跨站伪造请求、CSRF 盗用会话、上传文件留下孤儿。

关键不是"每一层都写"，而是**顺序**。顺序错了，最贵的检查会先跑，资源被白耗。

## 结构：按成本排序的校验链

```
POST /messages
  ├─ ① cap_request_body   体积上限（16KB，留言 multipart 放 4MB）→ 413
  ├─ ② @login_required    身份 → 303 跳登录
  ├─ ③ origin_ok()        Origin netloc 同源 → 403
  └─ ④ csrf_ok()          hmotp.compare_digest 常时比对 → 403
```

**①②③④ 的顺序就是成本从低到高**：

- 体积检查只看 `Content-Length`，O(1)
- 身份检查查 session，一次内存/DB 读
- Origin 检查只比字符串
- CSRF 要读表单/头里的 token，最贵

反过来（先查 CSRF）意味着：一个 8MB 的垃圾请求要先被完整解析才能被拒，而且是在 worker 里解析——这本身就是 DoS 面。

## 三个配套结构

**① 两套账要能回滚**

上传场景有两份状态：磁盘文件 + 数据库记录。任一边失败都要清另一边，否则留下孤儿文件（磁盘涨、库无记录、审计对不上）。

```python
stored = process_upload(file)      # 先落盘
try:
    insert_message(conn, stored)   # 再写库
except Exception:
    remove_stored(stored)          # 库里失败 → 删盘上的
    raise
```

顺序上"先落盘再写库"更好：库失败能删文件；反过来的话，库写成功但文件没落盘，就是一条坏记录。

**② 失败跳转用 303 不是 302**

302 语义是"临时重定向，方法不变"——部分客户端会把 POST 重放到新地址，等于重复提交。303 明确要求"改用 GET 访问新地址"，PRG（Post-Redirect-Get）必须用 303。

**③ 真实 IP 从右往左取**

`X-Forwarded-For` 是客户端可伪造的。只有当请求来自可信代理网段时才解析，且**从右往左找第一个不可信地址**——左边是攻击者填的，右边才是可信链路。从左往右取等于直接采信攻击者。

## 取舍

- **层数不是越多越好**：每层都增加调试路径，要有统一错误出口（一个 `errorhandler` 收敛格式）
- **应用层限体积是兜底**：真正的第一道应该网关挡（nginx `client_max_body_size`），应用层这层是为了"网关配置漏了也不死"
- **每次请求查库换安全**：单实例没问题，多实例时是 N 倍压力，需要缓存或 JWT 无状态化

## 什么时候别用

- **内部接口/内网服务**：没有跨站和外部攻击面，四道闸只留体积和身份两道
- **只读接口**：CSRF 和幂等都不需要，只留体积限制

## 判据

问自己：**"如果有人拿最便宜的方式打我，第一个挡他的检查有多便宜？"**
