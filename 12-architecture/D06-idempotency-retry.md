# D06 幂等与重试

> 出处：R02 架构卡片（aiohttp 爬虫的"四道闸"）

## 解决什么问题

调外部服务时，**失败是常态**，重试是必需。但重试带来两个新问题：

1. **重试本身可能违法**——429 限流时你越试越快，惩罚期越拉越长
2. **重试可能重复执行**——超时的那次请求，对方可能已经处理成功了，你重试就下了两单

只讲"限流"是不够的。完整的是**四道闸**：

```
连接池（同时在飞多少）
  → 限速（每秒发多少）
    → 重试（失败了怎么办）
      → 幂等（重试了怎么不重复）
```

## 结构

### ① 重试要按错误类型分支

```python
RETRYABLE = (ConnectionError, TimeoutError)        # 网络层
def should_retry(status):
    return 500 <= status < 600 or status in (408, 429)
```

- **5xx**：对方坏了，指数退避合理
- **429 / 503 + Retry-After**：对方说"你太快了"，**必须按头部等**，不能自己拍退避时间——拍短了继续挨罚，拍长了浪费时间
- **4xx（除 408/429）**：你请求错了，重试一万次还是错，**不重试**
- **连接错误/超时**：指数退避 + 抖动

一刀切用指数退避处理所有失败，是把三种不同语义压成一个策略。

### ② 幂等键只负责"算 key"，不负责去重

```python
def idempotency_key(method, url, body=b""):
    return hashlib.sha256(method.upper() + "|" + url + "|" + body).hexdigest()[:16]
```

它只保证：**同一个逻辑操作，每次算出来的 key 一样**。

它**不保证**"这个 key 只执行一次"——那需要原子存储：

```sql
CREATE UNIQUE INDEX idx_idem ON orders(idem_key);   -- SQLite/MySQL
-- 或 Redis: SET idem:{key} 1 NX EX 86400
```

流程是：**先占位，再执行**。占位失败说明重复，直接返回上次的结果。

### ③ 限速用"计划时间"

```python
delay = max(0.0, self._next - now)
if delay > 0:
    self.sleep(delay)
self._next = now + delay + interval     # 基于计划时间推进
```

如果睡醒后重新读真实时钟，每次调度延迟都会累加，跑一天间隔就漂了。

### ④ 连接池限的是"同时在飞"，不是 QPS

`ClientSession(connector=TCPConnector(limit=100, limit_per_host=10))`：

- 池满时请求**在本地排队等待**
- **排队时间也算进 `ClientTimeout.total`**
- 所以"服务端很快，但池子太小"照样会超时——这是最反直觉的一条

`limit_per_host=0` 的语义是"**不单独限制这一维度**"（回落到 `limit`），不是"禁止连接"。

## 取舍

- **幂等需要存储**：唯一索引/Redis 都要额外组件。只读接口完全不需要
- **重试放大流量**：下游已经过载时，重试会加剧。要有重试预算（如全局重试率上限）
- **抖动是必需品不是优化**：没有抖动的指数退避会让一群客户端同时重试，形成二次冲击

## 什么时候别用

- **只读 GET**：天然幂等，不需要幂等键
- **不可重试的操作**（如支付扣款，除非有幂等键）：宁可失败让人工介入，也不要盲目重试
- **下游明确不允许**（对方文档说不要自动重试）：遵守对方契约

## 判据

问自己：**"这次超时的请求，对方到底处理了没有？"** 答不上来，就必须有幂等键。
