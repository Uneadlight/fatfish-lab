## 〇、最高规范：没写前提的规格等于没写规格

> 2026-10-28 反转题实战教训（规格书在 `D:\work\规格书\`）。这一条比下面的收录标准更硬，适用于本目录所有卡片、以及任何写给别人的规格/接口说明/操作步骤。

**任何规则只写"怎么做"、不写"在什么前提下才这么做"，就是没写完。**

真实案例：B04 配置读取的规格里写「月/日不补零」。我脑子里的前提是"给人快速看"，但没写出来。对方按字面实现，测试要求 `2024-01-05` 这种补零格式，于是直接撞墙。注意：**「不补零」在"人看"前提下对，「补零」在"机器消费"前提下对——两条都对，取决于前提。** 对方没错，是规格没写全。

三类最容易漏的前提：

| 类型 | 该写什么 | 今天的例子 |
|---|---|---|
| **适用对象** | 这段输出是给人读的，还是给程序吃的 | 日期补不补零 |
| **环境假设** | 驱动、版本、编码、平台、时区 | 卡片写 "MySQL 用 `%s`"——前提是跑在 MySQL 驱动上 |
| **数量级** | 数据量、并发数、调用频率 | "多进程加速"——前提是 CPU 密集且单批数据够大 |

自检一句话：**把这条规则交给一个完全没有我脑内背景的人，让他严格按字面做，他会不会做错？** 会错 → 缺前提，不是他笨。

延伸：这条同样适用于「知识」本身。**知识没有对错，只有前提**——判断一条知识"适不适用"，比判断它"对不对"更准、更省力。

## 收录标准

只收「换个项目还能用」的东西。判据三条，缺一不收：

1. **可迁移**——在 ≥2 个单元里出现过，或者明显能跨项目用
2. **有取舍**——说得出"什么时候不该用"，没有反例的是口号不是模式
3. **能写成骨架**——有最小可运行的代码结构，不是一段描述

不收：单次调试过程、具体 bug 的修法。那些进 `D:\work\闭关\cards\09-踩坑与排障.md`（那里有 `kb_lint` 机器校验）。
