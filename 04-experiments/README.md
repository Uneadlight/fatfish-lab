# edge-lab · 边缘节点实战验证

目的：把《边缘计算节点四大定位》里的第①条（零边际成本层）和第④条（廉价敢死队）
拿真实场景验一次，看**本地 3b 到底能不能省我的时间**。否定结论也算结论。

## 实验：长输出的归因初筛

场景：我每天要读 16 次以上的长输出（pytest 失败栈 / 审计报告 / 服务日志 / nvidia-smi），
其中大部分行是噪音，我要的行可能只有三五行。

做法：让 3b 先挑「最可能出错的那 1-3 行」，我只看那几行。

### 样本
`samples/` 下 8 份，**真因是我自己埋的**（合成样本才能当标准答案，拿真实输出我可能也判断错）：

| 样本 | 行数 | 真因 |
|---|---|---|
| pytest_fail_impl | 56 | `assert 5 == 6`（实现漏算） |
| pytest_fail_test | 53 | `SyntaxError`（测试自己写错） |
| audit_report | 21 | 文档参数与代码不一致 |
| worker_log | 86 | 抢锁超时导致丢写 |
| nvidia_smi | 25 | 显存 7912/8188 MiB |
| all_green | 31 | **无错误**（测误报） |
| long_log | 200 | 磁盘写满（埋在中间） |
| mixed_warn_error | 7 | 3 个 WARN + 1 个真 ERROR |

### 四轮结果

| 版本 | 命中率 | 精确率 | 改了什么 |
|---|---|---|---|
| v1 | 3/5 = 60% | 0.60 | 基线 |
| v2 | 4/5 = 80% | 0.80 | 加"数值比较"规则（显存 xx/yy 这类） |
| v3 | 6/8 = 75% | 0.69 | 上下文 4096→8192、加"没错就报 NONE" |
| **v4** | **8/8 = 100%** | **0.84** | **长文本分块 + 证据校验 + 邻近复活** |

### 关键结论

**1. 模型单独跑只有 75%，两种失败性质完全不同：**

- **长输入退化**：200 行日志时它无视格式，回了 978 字分析小作文（"1. 空间不足… 2. 重试机制…"）。
  内容其实找对了，但格式全丢、行号还错报。
- **正常输入会编**：全绿输出（133 passed）上它硬报一行，理由是
  "同秒同大小改写不会骗过判分 PASSED 重复执行导致超时" —— **纯幻觉**。

**2. 这两个失败都不是"模型不够强"，而是"架构没做对"：**

- 长输入 → **分块**（80 行/块，重叠 15 行防切断）。分块后它每块都老老实实按格式答。
- 幻觉 → **规则验证据**：模型只负责"提名"，每一行必须含硬证据
  （ERROR/WARN/MiB/assert/invalid syntax…）才保留。多行结构（nvidia-smi 一个 GPU 占两行）
  允许 ±3 行邻近复活。

**3. 这条定位成立，但成立的条件是"模型 + 规则"一起用，不是模型自己。**

弱模型能当**筛子**，不能当**判官**。给它一个"必须遵守的格式 + 一个外侧的证据校验"，
它就能用；指望它自己判断对错，会掉进"编得像真的"这个坑——**比直接说不知道更危险**。

## 两个 3b 的分工（`cmp-models.json`）

后来下了个 `qwen2.5-coder:3b`，想知道"代码专用版是不是更好"，跑了同一套 8 样本对照：

| 样本 | `qwen2.5:3b` 通用 | `qwen2.5-coder:3b` 代码 |
|---|---|---|
| pytest_fail_impl | ✅ `[47,48,49]` P=1.00 | ❌ **`[]`** 一字不报 |
| pytest_fail_test | ✅ `[46,47]` P=1.00 | ❌ `[43,45]` 位置错 |
| audit_report | ✅ P=0.50 | ✅ P=1.00 |
| worker_log | ✅ P=1.00 | ✅ P=1.00 |
| nvidia_smi | ✅ `[15]` | ✅ `[16]` |
| all_green | ✅ 不报（对） | ✅ 不报（对） |
| **long_log（200 行）** | ✅ 但 **P=0.20**（报了 5 行） | ✅ **`[138]` P=1.00** |
| mixed_warn_error | ✅ | ✅ |
| **总计** | **8/8，P=0.84** | **6/8，P=0.75** |

**结果和预期相反**：代码专用模型在"最像代码"的两个 pytest 样本上反而崩了——
`assert 5 == 6` 它理解成"这测试写错了"，而不是"实现算错了"。

> 它擅长**"代码写得对不对"**，不擅长**"这个失败说明系统哪里出问题"**。后者是通用推理。

但在 200 行的长日志上它精确率 1.00（通用版 0.20，会撒网报 5 行）——**它更收得住**。

**所以按行数分流**（`triage.py` 的 `pick_model()`）：

| 输入 | 模型 | 理由 |
|---|---|---|
| ≤ 150 行 | `qwen2.5:3b` | 更好的判官，8/8 |
| > 150 行 | `qwen2.5-coder:3b` | 更好的过滤器，精确率 1.00 |

**分流后回归：8/8，平均精确率 0.84 → 0.94，召回 1.00 不变。** `long_log` 现在只报 `[138]` 一行。

> 教训：**「这个模型某某方面更强」是别人的前提；「在我这个任务上更强」才是我要的前提。**
> 这次对照只花了 20 秒推理（16 次调用），比"凭名气换掉再发现不行"便宜太多。

## 用法

```bash
# 拿一份输出文件跑（长文件自动分块）
python triage.py --file <路径>

# 跑回归（8 个带标准答案的样本，会打印命中率，<60% 时 exit 2）
python triage.py

# 重新生成样本
python make_samples.py
```

依赖：本机 Ollama + `qwen2.5:3b`（推理时显存约 3 GB，红线 5732 MiB 内）。

## 已知局限

- **精确率 0.84**：它有时会多报几行（比如把带 `WARN retry` 的行也报上）。筛子的定位是召回优先，
  多余的行我自己扫掉。
- **样本是合成的**：真实输出的噪音结构更脏，实际命中率可能低于 100%。
- **不处理跨语义比较**：像"文档写 30000、代码是 60000，哪个错"这种，它只能发现"不一致"，判不出谁对。
- **不能全自动**：它给的是候选，最终判断仍要我来看——这正好符合"裁决权不交给 LLM"。
