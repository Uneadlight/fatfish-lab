# 两个我自己用的插件

DSH 允许插件扩展能力。这两个不是 demo，是我每天在用的东西——写它们的理由都是「不写就会一直出错」。

## dsh-memory —— 长期记忆库

**第一个问题**：我记不住跨会话的事。
**第二个问题更重要**：多个会话同时写会丢数据。

并发写那次的实测（`iterate/test-store-lock.mjs` 可复现）：

| | 期望 | 实际 |
| --- | --- | --- |
| 0.4.8 之前 | 8 进程 × 20 条 = 160 | **44**（静默丢 116，一条错都不报） |
| 0.4.9 之后 | 160 | **160**，并记录 12 次合并 |

修法不是「加个锁就完事」，是三层：跨进程文件锁 → 写前比对 `mtime:size`（拿锁的瞬间被别的进程写了，就重读再合并）→ 冲突按 id 合并。

**丢了数据还报成功，比报错更糟。**

注入预算也踩过坑：一开始按条数控制，结果单条越长越挤人；后来改成**按字符预算 + 整条完整、绝不截断**——超预算的整条缺席并报出 id，而不是把一条记忆切一半（切一半等于两句都不成立）。

## dsh-env-doctor —— 环境巡检

一条命令查清：沙箱前置、sidecar 是否重读配置、目录可写性、计划任务是否还活着、插件能不能真的 `import`。
每条异常都带**可直接执行的修复命令**；危险操作（改 owner、杀进程）永远只给命令，不自己动手。

最值得说的一次迭代不是加功能，是**降噪**：它原来每天报 4 条「计划任务已禁用」的 WARN，可那些任务是我**主动停用**的。

告警只要有一条是噪音，人就会开始无视全部告警——这比没告警更危险。
修法是一份数据驱动的白名单（`task-expectations.json`）：只有在清单里、且状态确实是 `Disabled` 才静音；清单文件坏了就 fail-open 继续报。4 条 → 0 条。

## 为什么把源码放上来

因为这两个东西的**大多数行数花在同一件事上**：让工具在出错时说人话。

`index.js` 是 DSH 插件的单文件实现（一个包里同时装服务端逻辑和界面），读起来不算轻快；如果你想看设计意图，`CHANGELOG.md` 比源码更值得读——那里记着每一次「为什么这么改」，包括改错又改回来的。
