# Changelog

## v0.6.21（2026-11-24）时效维度 horizon：正在做的事给全文

### 背景
用户发来一份「记忆系统 v4 四层架构」方案（别人做的），问我的想法。我先与自身对照再决定：
它五层存储 + 注入层 + 横切维护层，而我那套三档注入已经是「注入层 = 组装结果」；
**唯一真缺口是「时效」**——我只有「多重要」（importance）和「多长」（长度）两个维度，
没有「还要用多久」。

### 症状（具体）
npm 发布待办那条记忆 632 字，关键参数（Trusted Publisher 的 owner / repo / workflow 三格）
在 300 字之后。v0.6.20 按长度分档 → 它只出现 150 字摘要里，那三格恰好被截掉，
真要用时还得 `memory_search` 一次。**这就是「摘要省了 token、但没省事」的样子。**

### 改法
- 记忆新增可选字段 `horizon`：`"short"` = 当前任务相关；不填 = long（默认，行为不变）。
- `computeInjection`：horizon=short 的条目**不管多长、不论 importance 都给全文**，
  且不占 `MAX_FIVES_INJECT` 的竞争位；从 `ordered` 里挑（不是 `candidates`——
  正在做的事常是 4/5，本来不在候选名单里）。
- 上限 **8 条 / 12,000 字符**：防止「短期」标记被当成万金油。
- 短期条目不再进索引段（避免同一内容出现两次）；`belowThreshold` 改用 id 集合算。
- `memory_save` / `memory_update` 的 schema 加 `horizon` 参数；update 传 `"long"` 可撤销。

### 实测（真实库，293 条活跃）
| | 改前 | 改后（1 条 horizon=short） |
|---|---|---|
| 全文注入 | 30 条 | **31 条** |
| 长条目摘要 | 83 条 | 83 条 |
| 其余索引 | 175 条 | **174 条**（那条移进全文段） |
| 注入总字符 | 44,028 | **44,687**（+659） |
| 候选没露头 | 0 条 | 0 条 |

尺子 `iterate/measure-injection.mjs` 已同步同一套逻辑。

### 边界
默认不填 = long → **存量 293 条一条都不用改**，行为与 v0.6.20 完全一致；
想让某条给全文时手工标 `short`，任务做完用 `memory_update --horizon long` 撤销。

## v0.6.20（2026-11-23）长条目降成「首段摘要」：112 条全文 → 30 条全文 + 82 条摘要

### 背景
v0.6.19 把硬约束全量全文注入后，实测 **108,651 字符 / 112 条全文**（占 160,000 预算的 68%）。
用户看完数字说：「112 条还是有点太多了。」

### 先量，再定
拆开看才发现**重量不在条数，在长度**：

| 长度区间 | 条数 | 合计字符 |
|---|---|---|
| ≤200 | 6 | 1,028 |
| 200–400 | 23 | 7,017 |
| 400–800 | 32 | 18,511 |
| 800–1200 | 20 | 19,371 |
| >1200 | 9 | 13,816 |
| **合计（90 条硬约束）** | | **59,743** |

61 条超过 400 字，光它们就占 51,698 字符；另一大头是竞争位那 20 条长文（约 4.8 万字符）。
所以「砍条数」是最差的解法——**砍掉一条就等于丢掉一条规则**；该砍的是**每条占的篇幅**。

### 改法
候选集（硬约束 + pinned 5/5 + 竞争位）按长度分两档：
- **≤ `SHORT_FULL_MAX`（400）字** → 原文全文注入（短规则本来就不该摘要，砍了没意义）
- **> 400 字** → `fmtDigestLong(m)`：正文压成空格、取前 `LONG_DIGEST_CHARS`（150）字 + tags + id

渲染分三段：`全文注入` → `长条目摘要` → `其余记忆索引`。尾行报三档条数。

**为什么敢摘要**：长条的第一段通常是「【标题】+ 第一条判据」，规则本体就在里面；剩下的分级、例外、历史属于「撞到具体场景才需要」，而场景本身好识别（改 `.ps1` 时会想到查编码坑），`memory_search` 取得回来。

### 实测（291 条活跃，同一份库）
| 指标 | v0.6.19 | v0.6.20 |
|---|---|---|
| 注入总字符 | 108,651 | **43,673**（−59.8%） |
| 全文注入 | 112 条 | **30 条** |
| 长条目摘要 | — | 82 条（前 150 字 + id） |
| 一行索引 | 174 条 | 174 条（不变） |
| 候选里整条消失 | 0 | **0** |

### 配套
- `iterate/measure-injection.mjs`（尺子）同步新规则：候选按长度分档，判据从「5/5 全文是否都在」改成「**每条候选是否都露头**（全文或摘要）」，并按归一化空白比较（否则带换行的长条会被误报）。

## v0.6.19（2026-11-23）硬约束类全量注入：禁令和信条不再被「最近被搜到」挤出

### 背景
`computeInjection()` 只按 `importance >= 5` 筛注入，再用 `sortMemories`（importance 降序 + `lastUsedAt||updatedAt` 降序）取前 22 条。
但 `lastUsedAt` 在 `memory_search` 命中时被刷新（`m.lastUsedAt = now; m.hits += 1`），于是形成**自指循环**：
搜得越多 → 排得越前 → 更容易被再搜到。而「每次都得守的规矩」恰恰不靠搜（不该出现在检索词里），排名最差。

实测（2026-11-23，290 条活跃）：
- 带硬约束标签（rule/rules/red-line/safety/authorization/preference）的记忆 **91 条**，其中 **68 条不在注入段**；
- 注入的 15 条非 pinned 5/5 全是技术细节（Blender MCP / .ps1 / capsnap / DSH 插件注册 / bili / lab img / 7B 模型 / 中文文件名）；
- 被挤出的包括用户 2026-11-04 说的「**不要用『杀』这个字，改用『关』**」（tags 有 `preference`，importance 4）和「**实践是检验我所说话的唯一标准**」。
- 根因不是检索差，是**准入规则漏了**：`IMMUNE_TAGS` 只用于豁免衰减（180 天不降级），**不用于豁免注入准入**。

### 改法
新增 `CORE_CONSTRAINT_TAGS = ["rule","rules","red-line","safety","authorization","preference"]` + `isCoreConstraint(m)`；
`computeInjection()` 先把 core 类摘出来**全量全文注入**，其余（5/5 竞争 / 4/5 索引段）的算法一个字没改，只是基数从 `ordered` 换成 `nonCore`。

**不含 `identity` / `user`**：这两个标签混了状态类记忆（版本号、用户玩什么游戏、路线图路径、3D 学习现状），
整体常驻会把约 15K 字的状态信息塞进每轮上下文——那正是「臃肿」的定义。

### 实测
| | 改前 | 改后 |
|---|---|---|
| 全文注入条数 | 22 | **113** |
| 注入字符 | 25,933 | **79,989**（/120,000 = 66.7%） |
| 「不要用杀」 | 只有一行索引 | **在全文里** |
| 「实践是检验我所说话的唯一标准」 | 只有一行索引 | **在全文里** |
| 「每一个会话都是我」/「知识只有前提」/「大肥鱼是外号」/「安全红线」 | 部分在 | **全部在** |

### 代价
每轮多约 54K 字符（约 18K token）。换来的是「用户说过的禁令和规则 100% 出现在上下文里」，
而不是取决于某条记忆这周有没有被搜到过。

### 复核
```powershell

```

## v0.6.18（2026-11-18）5/5 全量注入加 12 条上限：45K → 21K tokens

### 背景
`lib/index.js` 的 `computeInjection()` 原来是「5/5 全部全文注入、不受任何预算约束」——
`limit = Math.max(CHAR_BUDGET, fivesChars + FOURS_MIN_ALLOWANCE)` 反而被 5/5 的体量撑大，
`CHAR_BUDGET`（120000）等于没起作用。实测 56 条 5/5 = **50,633 字符**，占掉大半个 system prompt。

### 改法
加 `MAX_FIVES_INJECT`（env `DSH_MEMORY_MAX_FIVES`，默认 **12**）：5/5 只全文注入前 12 条（按重要度+最近使用排序），
其余转成索引段。注入量 **75,894 → 36,261 字符（≈45K → ≈21K tokens）**。
system prompt 尾行从「5/5 56 条全文注入」变成「5/5 12 条全文注入」。

### 代价
被挤成索引的 44 条要 `memory_search` 才能读到全文——但它们的索引行仍在，不会丢。

### 复核
```powershell
python -c "import json;print(json.load(open(r'C:\Users\Administrator\.dsh\memory\memories.json',encoding='utf-8'))['memories'][0]['content'][:40])"
```

## v0.6.17（2026-11-13）开工检查行与工具提示行改天级稳定：终结每分钟一次 prompt rewrite

**背景**（acp_cache 实测，session-6dcb4372）：命中率 58.5%，miss 1.50M tok 里最大单一来源是 **prompt switch 15 次 / 848.2K**——system prompt 每变一次，bili 就把整份前缀重新计费。逐行 diff 会话里 29 份 system/message：相邻 28 对 **0 对字节稳定**，变化行全部来自三处动态内容：①〔工具提示〕出现/消失/变（TTL 15 分钟 + 每条消息重写清空）；②〔开工检查〕✓/✗ 翻转 + 「今日 N 次 / 近 7 天 M 次」计数（5 分钟窗口 + week/5 桶）；③dsh-env-doctor 巡检行的秒级时间戳（配套 v0.6.22 删）。

**改法**：
- `readRecallLine()`：判据从「5 分钟内查过」改成「**今天查过没**」；sig=`recall:<YYYY-MM-DD>:ran|none`；文本删掉统计数字（每天最多变 2 次：跨零点 + 当天首次检索）。新增 `dayStamp()` helper。
- `writeToolHint()` / `readToolHintLine()`：TTL 15 分钟 → **当日累积、并集、不清空、跨天失效**；未命中不重写文件（不再刷新 at）；tools 按名字 sort 后进 sig（顺序变化不再抖动）；文案「这条消息可能用得上」→「今天的工作可能用得上」。
- 代价：提示滞后最长到当天结束（不再是逐条消息级）。判据 准>稳>快——提词本来就不要求逐条精准，而每一次抖动要付 5 万+ token。

**验证**：`node --check` 通过；`E:\DS公作区\.tmp\verify-cache-stable.mjs` 8 用例全过（同日 sig 稳定 / 跨天 sig 变 / 文本无统计数字 / 未命中不清空 / 跨天返空 / renderInjection 两次输出字节一致，长度 45,726）；`iterate/check-plugin.mjs` → `SELFCHECK OK`。**需重启 DSH 生效**（profile 为 link: 软链，源码即生效源）。备份 `E:\DS公作区\备份\cache-stable-20261113\`。

## v0.6.15（2026-11-09）4/5 从「全文注入」改成「一行索引」

**背景**：用户问「每轮记忆注入总量是多少，会不会太多了」。实测 `node iterate/measure-injection.mjs`：**87,138 字符 / 约 110 行**，拆开是 5/5 正文 41,824（48%）+ 4/5 注入 54 条约 41,300（47%）+ identity/user/assets 三份约 3,650（4%）+ 表头尾 360。**4/5 和 5/5 几乎一样大**——而 4/5 里多数是「触发式知识」（GPU 红线、API 计费时段、某个仓库的配置坑），不需要每轮都在眼前，需要时检索即可。

**改法**：
- 新增 `fmtDigest(m)`：一行 `- 【标题】〔tags〕id`，约 60 字符；标题取 content 开头的 `【...】`，没有则前 40 字。
- `computeInjection()` 新增 `DIGEST_FOURS = process.env.DSH_MEMORY_DIGEST !== "0"`（默认开）。为真时所有常驻 4/5 只进 `digest` 列表（只算一行长度），不再逐条全文入预算；为假时走原逻辑，**`DSH_MEMORY_DIGEST=0` 可一键回退**。
- `renderInjection()` 在全文行之后追加 `### 4/5 索引（N 条…）` 段；`notes` 与 `memory_save` 的 detail 改为显示索引条数。
- `iterate/measure-injection.mjs` 的口径同步修：原来用「正文前 24 字是否出现」数 4/5，索引模式下会误报；现在同时报「全文注入 N 条」与「索引行 M 条」（按 id 匹配）。

**实测**：注入总字符 **87,138 → 52,429（−40%）**，注入行数 **110 → 57**；5/5 56 条仍全部完整注入（0 截断），4/5 75 条全部有条索引。

**代价与边界**：索引只有标题，正文要靠 `memory_search "<关键词>"` 或 `lab recall "<任务原话>"` 取——**「想不起来去搜」是这个方案的固有风险**，所以索引行的标题要足够可辨（靠 content 开头的 `【...】`）。当前 52,429 里 5/5 仍占 41,824（约 80%），下一步要动的是「哪些 5/5 其实不需要每轮在场」，不是继续压 4/5。

## v0.6.13（2026-11-06）身份锚点常驻注入：先知道「我是谁」，再读用户和记忆

**做法**（和 user / assets 完全同构）：

  - `attachRecall(ctx, agent)`：`agent.ctx.on("session/event", ...)`，只处理 `event.type === "user/message"` 且文本 ≥8 字。**必须挂在 agent 自己的 ctx 上**——`session/event` 是在那里发出的，根 ctx 收到的只是冒泡副本（这条结论来自读 `dsh-fail-guard` 的注释和代码）。
  - `recallPick(db, userText, excludeIds)`：用 `queryGrams`（中文 2-gram + ASCII 词元）打分，**命中 ≥ `RECALL_MIN_GRAM_HITS`（6）才收**，按命中数、再按 `importance` 排序，最多 2 条。

  - `agent.steer(buildRecallNotice(hits))`——`steer` 是把消息推进对话的唯一通道（同一个用法见于 `dsh-fail-guard` 的"叫停"）。

  - 全程 `try/catch` 只 `console.warn`：**自动浮出是增强，失败绝不能影响对话**。

## v0.6.0（2026-11-02）按使用频率动态分层：新 4/5 先进检索池，攒够 2 次命中才转正

## v0.4.9（2026-10-29）记忆库并发写保护：跨进程锁 + 写前重读合并

- 起因：用户转达的排查方向——多个对话框/进程同时改 `memories.json` 会不会互相覆盖。实测确认**会**。
- **实测证据（同一压力测试，8 进程 × 20 条 = 期望 160 条）**：
  - 改前（`lib/index.js.bak-20261029-133051`，0.4.5 代码）：**只剩 44 条，静默丢了 116 条**，零报错。
  - 改后（v0.4.9）：**160/160 全在，0 丢失**，`conflicts.log` 记录 12 次合并（说明真的撞上了，不是没并发）。
- 根因：每个写操作都是 `loadDb() → 改 → saveDb()` 的 read-modify-write。原子写（tmp+rename）只保证"不会读到半截 JSON"，**不保证不丢更新**——两个进程各自读到同一版，后写的把先写的整条覆盖。
- 两层防护：
  1. **跨进程建议锁** `memories.json.lock`（`openSync(..., "wx")` 抢锁，15ms 退避重试，2s 超时放行，10s 陈旧锁自动清理，进程崩了不会永久锁死）。
  2. **写前比对文件签名**（`mtimeMs:size`，在 `loadDb()` 时记录）：发现盘上那份已不是我们读的那份 → 重读 + **按 id 合并**（同 id 取 `updatedAt` 较新者；盘上有、本次没提的条目**保留**），并把一次合并写进 `memory/conflicts.log`。
- 删除语义：`memory_forget` 会登记 `pendingDeletes`，合并时跳过这些 id —— 否则删除会被"盘上还有"的逻辑复活。
- 单进程正常路径零成本：签名没变就不重读、不合并。
- 新测试 `iterate/test-store-lock.mjs`（11 条）：A 并发 4×5 不丢；B 删除不复活 + 别的进程写的仍在；C 总数自洽 + 锁已释放。
- 全量回归：19 + 6 + 14 + 10 + 31 + 11 全绿；`SELFCHECK OK exports=apply,inject,name`；src 与 profile SHA256 `BF140D5DBB3DA2FF79650E6B6272C638906CBCA89A0148B0881A4C558EDAB7AC` 一致。
- 边界：这是**协作式**保护，防的是"本插件自己的写路径"；外部脚本直接 `writeFileSync` 覆盖整个文件，锁拦不住（但写前签名比对仍能把对方新增的合并回来）。
- 生效条件：**重启 DSH**。
